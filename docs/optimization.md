# Ранжування: цикл Python → вирази NumPy (лаба 8)

Корпус `index_big.bin`: 230 документів (23 діалоги ×10), 21 778 термінів. Схема: `Index.arrays` (`findex/arrays.py`) будує для кожного терміна, який шукали, два масиви `int32` (`doc_id`, `tf`) і один масив `int32` довжин документів. BM25 і TF-IDF рахуються виразами над масивами, топ-k береться через `np.argpartition`. Еталонний цикл із лаби 3 (`ranking.rank`) лишився як контрольна реалізація: `ranked_search(..., fast=False)`.

Вимірювання: `uv run python scripts/bench_rank.py index_big.bin`. Ryzen 7 5800X, Windows, Python 3.11, BM25, k = 10; кращий із 7 серій (кожна не коротша за 50 мс), мс на виклик. Один прогін, тож останній розряд це шум.

## Що видно з таблиці

- **Реальний корпус: ×7-8.** Python-цикл платить за кожен постінг виклик методу `score` (`index.num_docs`, `avg_doc_length`, `math.log`, створення об'єкта `SearchResult`); NumPy рахує `idf` один раз на терм, решту виразом над масивом, а топ-k бере без створення об'єктів.
- **Рідкісний терм: ×0,7, тобто NumPy повільніший.** Це 10 постінгів: Python-цикл робить 10 викликів `score` (19 мкс), а NumPy має фіксовану ціну: два масиви довжини `N` (`scores`, `touched`), ≈ 15 викликів NumPy по кілька мікросекунд кожен (оцінка, не вимірювання) і лише потім корисна робота. Нижче приблизно 20-30 постінгів цикл Python виграє. Для реального запиту це байдуже (різниця 7 мкс), але на таблиці видно, що вигода NumPy не безкоштовна.
- **Довгі списки: ×42-78.** Тут фіксована ціна розчиняється. Але при 10-кратному зростанні даних Python-цикл росте рівно в 10 разів (26,9 → 278 мс), а NumPy у 19 (0,34 → 6,7 мс), тому виграш на 200 000 документів менший, ніж на 20 000. *Гіпотеза (не перевірена):* масиви в 200 000 елементів уже не вміщуються в кеш процесора, а `scores[ids] += part` і `np.argpartition` обмежені пам'яттю, а не обчисленнями.
- **Перший виклик дорожчий.** Перетворення списку `Posting` на масиви коштує 0,1-0,4 мс на реальному корпусі і 3-32 мс на синтетичному (порядку одного-двох викликів Python-ранжування). Для сервісу це одноразово, для одиничного `findex search` це дрібниця на тлі завантаження індексу (1,6 с).

## Порядок результатів збігається з лабою 3 (тест)

`tests/test_arrays.py` порівнює `rank_fast` з `rank`: 150 випадкових індексів для кожного з 4 скорерів (BM25 з двома наборами параметрів, TF-IDF з нормалізацією і без), індекс із `corpus/` (4 скорери × 5 запитів × 3 значення k), `candidates`, `k` більший за кількість кандидатів, відсутні терміни, документи нульової довжини, невідомий scorer (запасний шлях до `rank`). Збігаються і порядок документів, і бали (`rel=1e-12`). Щоб порядок не розходився при рівних балах, логарифми `tf` беруться з таблиці `math.log` (а не `np.log`), бали різних термінів додаються в тому самому порядку, а при рівності першим іде документ із меншим `doc_id`.

## Обмеження цього рішення

Масиви будуються з Python-списків `Posting` при першому зверненні, тому обидва представлення живуть у пам'яті одночасно, а завантаження індексу (1,6 с на `index_big.bin`, переважно створення мільйонів об'єктів) не прискорилось. Булева частина запиту (`merge_and`, `Term.evaluate`) лишилась на Python.
