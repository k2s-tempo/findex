# Профілювання до оптимізації (лаба 8)

Записано **до будь-яких правок коду**. Корпус `data/big`: 230 файлів, 62 МБ (це 23 діалоги Платона ×10, тобто копії: словник лишається 21 778 термінів, зростає довжина списків постінгів і кількість токенів, 10,7 млн). Запит для пошуку: `justice virtue courage` (збігів 140, df: 210 / 220 / 140). Машина: Ryzen 7 5800X, Windows, Python 3.11.

Інструменти: `cProfile` (`docs/prof-*.pstats`, у git не входять), `py-spy` (flame graph: `docs/flame-index.svg`, `docs/flame-search.svg`), Scalene (розділ нижче).

## Індексація: три найдорожчі місця (cProfile, 21,4 с)

1. **Цикл у `build_partial` (власний час 6,4 с, 30%).** По одному токену: `enumerate`, `local[token].append(pos)`, потім `postings[term].append(Posting(...))`. *Гіпотеза:* це байткод Python, а не нативний код: 10,7 млн ітерацій по ~0,6 мкс. Векторизувати навряд чи вийде, бо токени приходять потоком зі списків рядків; найімовірніше прискорення дає зменшення роботи на токен.
2. **Токенізатор (`tokenize`, 5,6 с власного + 1,1 с `Match.group`, разом ≈ 32%).** 10,7 млн викликів генератора й створень `re.Match`. *Гіпотеза:* час іде не на пошук збігу самим рушієм `re` (нативний код), а на накладні витрати на токен: відновлення генератора, об'єкт `Match`, виклик `.group()`. `re.findall` повертає рядки одним нативним викликом, тож має бути суттєво швидшим при тому самому результаті.
3. **Збереження (`save_array`, ≈ 3,3 с, 15%).** Усередині `_u32_bytes` генератор позицій `(pos for p in plist for pos in per_doc[p.doc_id])` на 10,7 млн елементів (≈ 2,0 с) і `array('I', ...)` (≈ 1,1 с). *Гіпотеза:* знову Python-цикл по кожному цілому. Якщо позиції лежать у масиві NumPy `int32`, запис це один виклик `tobytes()`.

Окремо: `io.open` 2,36 с на 289 викликів (8 мс на файл, 11%). *Гіпотеза:* це не Python, а ОС (сканування файлів антивірусом Windows), тож у коді тут нічого оптимізувати.

## Пошук: три найдорожчі місця (cProfile, 0,39 с на 300 запитів)

1. **`scoring.score` (126 000 викликів, ≈ 0,155 с, ~40%).** 420 викликів на запит. Кожен викликає `index.num_docs` (властивість: `len(docs)`), `index.avg_doc_length` (`cached_property`) і `math.log`, хоча `idf` однаковий для всіх постінгів терміна. *Гіпотеза:* це накладні витрати виклику Python-методу на кожен постінг, а не арифметика. Саме це забирає NumPy: `idf` рахується раз на терм, а BM25 стає виразом над масивами `tf` та довжин документів.
2. **Збір топ-k: `rank` (власний 0,069 с) + `heapq.nlargest` (0,080 с), разом ≈ 38%.** Створення `SearchResult` для кожного кандидата і 47 400 викликів `__lt__` згенерованого dataclass-а. *Гіпотеза:* порівняння об'єктів на Python це більша частина часу `nlargest`. `np.argpartition` бере топ-k на масиві чисел без жодного об'єкта.
3. **`merge_and` (600 викликів, 0,079 с, ~20%).** Два вказівники в Python-циклі. *Гіпотеза:* чистий байткод, ~140 елементів на перетин: тут нативний `np.intersect1d` теж виграє, але лаба цього не вимагає, тому лише спостереження.

## Python чи нативний код

Для пошуку майже весь власний час припадає на Python-функції (`score`, `rank`, `merge_and`); нативними є лише `math.log`, `len` та C-частина `heapq` (разом ≈ 10%). Для індексації це змішано: токенізація (регулярка) нативна лише частково. Scalene нижче має підтвердити цю оцінку або спростувати її.

## Спостереження поза трійками

- Завантаження індексу (1,6 с) і старт CLI (2,4 с у цілому) значно перевищують час самого пошуку (0,5 мс). *Гіпотеза:* завантаження породжує мільйони Python-об'єктів: `Posting(d, t)` на кожен постінг і `list.tolist()` на 10,7 млн позицій. Для сервісу це одноразова ціна при старті, для `findex search` в CLI це майже весь час.

## Старт CLI (`python -X importtime`, до правок)

`import findex.cli` ≈ 407 мс сумарно. Найдорожче: `findex.web.cli_cmd` ≈ 109 мс (через `findex.web.settings` тягне `pydantic_settings`, ≈ 44 мс) і `findex.crawler` ≈ 98 мс (`httpx` ≈ 61 мс); `typer` ≈ 44 мс. *Гіпотеза:* ці імпорти потрібні лише командам `serve` і `crawl`, але їх платить кожен запуск `findex`, зокрема `search`. Перенос імпорту `Settings` у тіло `serve` має зняти ≈ 100 мс (це мій регрес із лаби 7); те саме для `crawl` дало б ще ≈ 100 мс, але це код лаби 6.
## Scalene (Windows, Python 3.11, scalene 2.4.0): результат неінформативний

Запуск: `scalene run --cli --cpu-only --profile-all` на 20 000 запитів (11,5 с). 83% часу Scalene приписав рядку `threading.py:975` (виклик цілі потоку), причину не з'ясовано; на файли findex припало ≈ 12,6% (`scoring.py` 5,9%, `ranking.py` 3,8%, `storage.py` 1,2%, `merge.py` 1,0%, `query.py` 0,8%), і частку Python у цих рядках він майже не зареєстрував. Розділити «Python / нативний код» за цими цифрами не можна. Висновок про Python-накладні витрати тримається на cProfile (власний час у Python-функціях `score`, `rank`, `merge_and`) і підтверджений експериментом: заміна циклу на NumPy дала ×7 на реальному корпусі й ×42-78 на довгих списках (`docs/optimization.md`).
